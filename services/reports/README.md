# Норма трафика SEO (схема `reports`) — итоги работы 2026-09-30

Цель: построить «Норму трафика SEO» для ddos-guard.ru (ru) и en — сезонные индексы органического трафика и
спроса, на основе которых отчёт показывает, насколько факт выше/ниже нормы. Данные: GA4 и Яндекс.Метрика
(трафик), Google Search Console (состав), Wordstat (спрос по продуктам, бренду и контрольной корзине).

## Результат в двух строках

- Для **ru** норма построена (GA4 — основной ряд, Метрика — для сверки): **с апреля по август 2026 органика ниже
  нормы на 13–34% (GA4) и на 13–32% (Метрика)**. Месяцы до марта 2026 «в норме» по построению (они сами формируют
  норму, см. «Как устроена норма» п. 7), поэтому подтверждением модели не являются.
- Для **en** норма не строится (устойчивый тренд вниз, сезонность неотличима от тренда).
- **Спрос Wordstat (ru)** собран и посчитан равновесным индексом фраз: контрольные общие запросы стабильны (+4…+11% год
  к году), поэтому снижение спроса в теме реальное. Август 2026 к августу 2025: Хостинг −64%, Главная −33%, VDS −32%,
  L7 −31%, DS −26%, Заказ атаки −24%, L3-4 −18%; бренд −2% (норма бренда в коридоре). Нормы спроса есть для DS, L3-4 и
  бренда (DS ниже нормы с мая по июль), для остальных рядов спрос падал уже зимой — смотреть год к году
  (`reports.v_demand_index_yoy`). Падение продуктового спроса сопоставимо с падением органики (−27…−37% год к году
  в июле–августе), но информационные страницы (основная потеря Google) продуктовым спросом не описываются.

## Как устроена норма

1. **Данные** с 2024-09-16 (день разделения сайтов ru/en; более ранние несопоставимы).
2. **Сезон** = 12 месяцев подряд от первого полного месяца (окт 2024 – сен 2025, окт 2025 – сен 2026).
   Индекс месяца = среднее в день за месяц / база сезона (среднее по месяцам, пригодным во всех сезонах),
   усреднённое по сезонам. Индексы считаются по «среднему в день», иначе февраль занижается на ~10%.
3. **Не входят в расчёт:** неполные месяцы, сезоны с недостатком пригодных месяцев (`--min-months`),
   аномальные месяцы (автодетект по отклонению от соседних месяцев + ручной список `seasonality_events`,
   действия `exclude`/`keep`, область `traffic`/`demand`/`all`).
4. **Норма месяца** = уровень × индекс × дни. Уровень — среднее «значение в день / индекс» по пригодным месяцам
   **последнего сезона** (месяцы прошлого сезона тянули бы уровень к его устаревшей базе). **Коридор** =
   ±max(10%, 2 × среднеквадратичное отклонение пригодных месяцев от нормы): тренд тоже расширяет коридор.
5. Для месяцев, где у GA4 нет пригодных наблюдений (июль–август), индекс берётся из Метрики того же сайта
   (`confidence = fallback`).
6. **Проверка надёжности:** норма не строится, если уровень соседних сезонов различается больше чем на 20% или
   коридор шире 35% (`--max-trend`, `--max-band`), либо ни у одного месяца индекс не посчитан по двум сезонам
   (иначе норма просто копирует факт). Так отсеиваются все ряды en и Яндекс ru по GA4.
7. **`in_sample`.** Месяцы, вошедшие в расчёт индекса и уровня, сравниваются с нормой, построенной на них самих,
   поэтому «в норме» по ним верно по построению. Колонка `reports.seo_traffic_norm.in_sample` = true для таких
   месяцев; в отчёте они помечены ‡. Проверкой нормы служат только месяцы с `in_sample = false`
   (исключённые аномалии и новые месяцы). Для своих отчётов фильтруйте по этой колонке.
8. **Неполные месяцы** никогда не сравниваются с нормой, в том числе если они попали в ручное исключение
   (`seasonality_events`).

## Важные выводы

1. **Падение органики ru с апреля 2026 реальное и не сезонное.** GA4: −15% (апр), −18%, −31%, −20% (июль),
   −9% (август, в коридоре), −31% (сентябрь, неполный месяц) относительно нормы; Метрика: −16%, −20%, −29%,
   −34%, −24%, −36%. Его видят GA4, Метрика и GSC (внутри 2026 небрендовые клики −63% с марта по сентябрь).
   В настройках тега GA4 с ноября 2025 по август 2026 изменений не было.
2. **Кто теряет.** По GA4 до апреля Яндекс рос (год к году +3…+72%), Google был около нуля (−14…+15%).
   С апреля Яндекс просел на 25–45% (апрель–июль) и частично вернулся (по Метрике август −4%, сентябрь −10%);
   Google снижается всё сильнее без отскока (GA4 −10% → −32%, Метрика −18% → −46%). С марта по сентябрь GA4-органика
   потеряла ~5,7 тыс. сессий в месяц, около 88% — Google (11 240 → 6 241).
3. **Что теряет в Google (GSC, клики в день).** Информационные страницы (блог, термины, гайды): 78,6 (апрель) →
   25,5 (август), −68%. Продуктовые небрендовые: 10–12 → 6,5 (−45%; малая база). Бренд стабилен: 45–53.
   Небрендовые: позиция 7,9 → 11,4, показы −42%, CTR 0,43% → 0,33%.
4. **Два механизма потерь по запросам** (Q4 разбора): потеря позиций на головных информационных запросах
   («кибербезопасность» 2,5 → 6,5, «dns сервер» 3,0 → 14,1, «днс сервер» 3,4 → 22,9, «vds сервер» 9,3 → 13) и
   падение кликов при неизменной или улучшившейся позиции («ddos-атака», «tcp handshake», «arp», «модель osi») —
   похоже на изменение выдачи (гипотеза, не проверена).
5. **Сезонность (ориентир, ru).** Выше среднего: осень (окт–ноя) и март; ниже: январь и лето (Метрика: июль 0,80,
   август 0,72). Индекс у апреля–июня и сентября по одному сезону. Норма GA4 ru: окт 12 446, ноя 12 657, дек 12 709.
6. **en: нормы нет.** Уровень сезонов различается на 21–38%, Метрика en: 6 618 (окт 2024) → 1 977 (сен 2026).
7. **Бренд в GSC.** С января 2026 клики по бренду выросли с ~1–2 до ~41 в день, потому что главная стала показываться
   по брендовым запросам (раньше — случайные подстраницы); спрос на бренд по показам не вырос. В GA4/Метрике это
   не видно. Небрендовый трафик нужно держать отдельно от бренда.

## Проблемы, с которыми столкнулись

Данные:
1. **Сбой GA4 30.07–17.08.2025** (ru: 15 дней пропущено, en: 15–17.08); месяцы неполные, в Метрике они в порядке.
2. **GSC в БД неоднороден:** сен 2024 – янв 2025 ~400–1000 строк в день, фев–июль 2025 ~60 (почти пусто), с
   августа 2025 ~4–5 тыс.; пропуски дней ноябрь 2025 (20), декабрь (23), январь 2026 (24) — сбои cron
   (уже отмечены в `services/analytics/gsc-datalens-dashboards.md`); разрыв бренда в январе 2026. Лимит 25 000
   строк в день не достигается (максимум ~6 тыс.).
3. **GA4 и Метрика расходятся по Google:** отношение сессий выросло с 1,31 до 1,81; по en разбивка Яндекс/Google
   различается в 2,4 раза (Яндекс за 36 мес.: GA4 ~48 тыс., Метрика 114 тыс.).
4. **В «Яндекс» попадали не поисковые источники** GA4 (`oauth.yandex.ru`, `yandex.promopages`, `practicum`, `alice`,
   ~14%) — исправлено: только поисковые домены.
5. **Мало сезонов:** данные несопоставимы до 16.09.2024, поэтому всего два сезона; у ru в GA4 данные вообще с
   середины 2024.
6. **Wordstat** — российский Яндекс, для en не годится. Оплата Yandex Cloud решена, спрос собран (данные до августа 2026;
   сентябрь на 1 октября ещё не опубликован — общий пересбор после публикации).
7. Метрика: сэмплирование (дробные значения → округляем), пустое название канала (`(not set)`).

Окружение и код (исправлено в ходе работы):
8. **Заглушка в окружении сервера** `YANDEX_METRIKA_COUNTER_ID=your_counter_id` перебивала `.env` (dotenv не
   перезаписывает существующие переменные); найти и убрать её из профиля оболочки (`~/.bashrc`, `~/.profile`,
   `/etc/environment`).
9. Сдвиг дат на день из-за `toISOString()` в поясе UTC+3.
10. Таблицы `reports.*` были созданы более ранней версией схемы — добавлены `ALTER TABLE … ADD COLUMN IF NOT EXISTS`.
11. Ошибка `GROUP BY` в запросе сегментов GSC (найдена только на сервере) — исправлена; теперь SQL проверяется на
    настоящем движке (DuckDB), а не только парсером.
12. Норма для рядов с трендом получалась бессмысленной (коридор ±336%) — добавлена проверка надёжности.

## Что осталось открытым

1. **Причина падения органики ru с апреля 2026.** В заметках явного события нет; настройки GA4 не менялись.
   Ближайшие релизы: страница L3-4 (16.04), регистрация/вход (04.05), падение релевантности DS (18.05). Нужен разбор
   по страницам/запросам Google (запросы Q2/Q4 уже есть), проверка изменений выдачи.
2. **Причина сбоя GA4 30.07–17.08.2025.** В истории тега записей за период нет; нужна история версий контейнера GTM
   и релизы сайта (14.08.2025 — редизайн дашборда ЛК).
3. **Брендовые клики GSC (+40 в день с января 2026) не видны в GA4/Метрике.** Гипотеза: существующие клиенты идут
   на главную за входом в ЛК, и сессия теряется (редирект до загрузки счётчиков). Не проверено.
4. **Спрос по информационным страницам не оценён.** Основное падение клика Google пришлось на блог и термины,
   а продуктовый спрос их не описывает. Нужен пул информационных запросов из GSC (порядка тысяч фраз, около суток
   сбора из-за квоты Wordstat; фразы фиксируются так же, как продуктовый пул). Сентябрь 2026 в Wordstat — общий
   пересбор после публикации данных. Для en нужен другой источник спроса (Google Trends / Keyword Planner).
   Продуктовый пул: группы Топвизора + фразы из GSC (`demand-pool-from-gsc.js`), «Заказ атаки» вынесен отдельным
   рядом, дубли Wordstat (порядок слов, словоформы) отключены `demand-pool-dedupe.js`; DDG VM, Cloudflare,
   dCAPTCHA, «Аудит ИБ», ОРИ исключены.
5. **Расхождение GA4 и GSC по уровню** и дрейф отношения GA4/Метрика по Google не разобраны. Для проверки нужна выгрузка
   GA4 по посадочным страницам (`landingPage`) против кликов GSC по тем же страницам.
6. **en:** норма не строится; вернуться, когда накопится больше сезонов или выяснится причина устойчивого снижения
   после разделения сайтов.
7. **Ориентировочность нормы:** два сезона; пересчитать через несколько месяцев. Регулярный запуск (cron) и
   автообновление отчёта не настроены.
8. **Непроверенные гипотезы о высоких месяцах ru:** Cloudflare-события (блокировка ECH окт 2024, «резание» трафика июнь 2025,
   реестр ОРИ ноябрь 2025) и кампании в марте (интеграции 21–24.03.2025, рассылка/таргет к 8 марта 2026) могли поднять
   осень и март; проверить, выделив брендовый и небрендовый органик.
9. **Нормы по сегментам (бренд / продукты / информационные)** не строятся из-за разрыва ряда GSC в январе 2026;
   пока даётся только состав. GSC-пропуски ноябрь 2025 – январь 2026 можно догрузить бэкфиллом сборщика.
10. **Решения по параметрам:** пороги надёжности (20% / 35%), включение Яндекса ru по GA4 (тренд +24%),
    список аномальных месяцев в `seasonality_events`.

## Покупки из organic и KPI-диапазоны по продуктовым группам

Данные (CSV не хранятся в git, файлы кладутся на сервер вручную или указываются через `--products`/`--overall`): `services/reports/data/organic_monthly_products.csv` (новые плательщики и оплаты первого дня по группам L7, L3-4, DS, VDS,
Хостинг) и `organic_monthly_overall.csv` (итог по сайту). Правило organic задаёт выгрузка. Схема: `purchases_schema.sql`.

```bash
node scripts/purchases-kpi.js            # отчёт по CSV, БД не нужна
node scripts/purchases-kpi.js --apply    # записать reports.purchases_monthly / purchases_overall_monthly / purchases_kpi
npm run test:purchases-kpi
```

Метод: середина диапазона на следующий квартал = среднее за последние 4 квартала (без сезонных индексов: покупок мало, чтобы
их выделить). Границы — 80% интервал: плательщики по отрицательному биномиальному, сумма по месячному разбросу. Каждый
прошедший квартал проверяется по диапазону, построенному на 12 месяцах ДО него. Сигнал — два квартала подряд ниже нижней
границы. Надёжность: `ok`, `low_volume` (менее 8 плательщиков в квартал: DS), `regime` (L3-4: триал с 2025-09,
страница и скидка 99% с 2026-04; без платёжной выгрузки по «полной цене» и «тесту» диапазон только ориентир).
Новые данные: заменить CSV (те же колонки) и запустить `--apply` повторно, загрузка идемпотентна.

HTML-отчёт `reports/seo-norm-datalens`: блок «Покупки из organic» (две таблицы: плательщики и сумма, по кварталам с диапазоном и KPI на
следующий квартал, строка «Весь сайт» и текстовые выводы). Из БД: `queries.sql` отдаёт `purchases_monthly` и `purchases_overall`,
`build.js` считает диапазоны тем же кодом, что `scripts/purchases-kpi.js`. Перед выгрузкой выполнить `purchases-kpi.js --apply`.

## Трафик по страницам входа и связь с покупками

`scripts/traffic-organic-landing.js` собирает по API органические сессии по странице входа (GA4: `landingPage`, Метрика: `startURLPath`),
по полным месяцам, поисковикам Google / Yandex / Other → `reports.traffic_organic_landing` (схема `traffic_landing_schema.sql`).
Представления: `v_landing_page_group` (страницы групп из Топвизора), `v_traffic_landing_group_monthly` (сессии по группам L7, L3-4, DS,
VDS, Хостинг, Главная, Информационные, Прочее), `v_purchases_vs_traffic_quarterly` (квартал × группа: сессии на страницы группы,
новые плательщики, конверсия на 1000 сессий). «Информационные» (блог, terms, tutorials, technologies, case-studies, osi-model) в
конверсию продукта не входят: покупатель мог начать с блога.

```bash
node scripts/traffic-organic-landing.js --dry-run                 # проверка без записи
node scripts/traffic-organic-landing.js --source ga4              # основной источник
node scripts/traffic-organic-landing.js                           # GA4 и Метрика
npm run test:traffic-landing
```
Страницы с группой определяются по `target` фраз в Топвизоре (проект ddos-guard.ru). Страница с трафиком, но без target, попадает в
«Прочее» (если не информационный раздел): проверить «Прочее» после первой загрузки.

`v_purchases_vs_traffic_quarterly` и `v_traffic_vs_payers_site_quarterly` помечают квартал как неполный, если в GA4 есть месяц со сбоем
сбора (`v_ga4_months_complete`, например июль–август 2025). `payers_per_1000` — не конверсия страницы: покупатель приходит не только
на страницу продукта (на главную приходится ≈8–9 тыс. сессий в квартал против ≈1,5 тыс. на все продуктовые страницы), а с главной,
из блога и т.д.; показатель годится только для динамики.

Скрипт сам берёт подключение к БД для `psql` из `.env` (PGHOST, PGUSER, PGPASSWORD, PGDATABASE); переменная `DATABASE_URL` не нужна. Для ручного запуска `psql` в других местах README: `set -a; . ./.env; set +a` или те же PG*-переменные.
Трафик собирается только для ru (`--site ru`): норма по en не строится, а Метрика en отдаёт ошибку 400 (запрос слишком сложный) на старых месяцах.

  обновления данных их надо перечитать и поправить в `reports/seo-norm-datalens/template.html`.

## Клиентский путь из GA4 (по customer_id)

`customer_id` в событиях GA4 совпадает с id клиента в админке (подтверждено). `scripts/ga4-customer-journey.js` выгружает по API
события регистрации, корзины, оформления, способа оплаты и оплаты по клиенту с каналом ПЕРВОГО визита пользователя и оплаты с купоном,
валютой, суммой и способом оплаты → `reports.ga4_customer_events`, `reports.ga4_customer_purchases` (схема `ga4_customer_schema.sql`).
Вью: `v_ga4_customer_journey` (клиент: канал, регистрация, первая оплата, срок, число оплат, тест L3-4 по купону `L3_PAID_TEST_99`),
`v_ga4_registration_funnel_monthly` (регистрации месяца по каналу и доля оплативших в тот же день, за 30 и 90 дней).

```bash
node scripts/ga4-customer-journey.js --dry-run     # проверка без записи
node scripts/ga4-customer-journey.js --from 2026-01
npm run test:ga4-journey
```
Ограничения: нет цепочки страниц (нужен BigQuery); оплата идёт с сервера (хост «(not set)»), канал берётся по пользователю, не по сессии;
события шагов мастера (L7 Шаг N и др.) в мае и июле 2026 менялись — для воронки использовать registration → begin_checkout →
add_payment_info → purchase; `customer_id` внутренний, в отчёты наружу не выводить.

## Путь посетителя по визитам (Яндекс Метрика, Logs API)

В GA4 `cid_ga4` не заполняется (0% событий), поэтому путь по страницам через GA4 API не собрать. `scripts/metrika-visit-paths.js` выгружает
визиты 2026 года через Logs API Метрики (по ClientID, анонимно), складывает в `tmp/metrika-visits/` (не в git) и считает: когорты новых
посетителей по типу входной страницы (доля зарегистрировавшихся и оплативших за 30 дней), число визитов до регистрации и оплаты,
долю тех, чей путь начался с информационных страниц или проходил через них. Цели: регистрация 293671240, покупка 326195013.

```bash
node scripts/metrika-goals-audit.js                    # список целей Метрики с числом достижений
node scripts/metrika-visit-paths.js --from 2026-01     # выгрузка (месяц = запрос, готовые месяцы пропускаются) и сводки
node scripts/metrika-visit-paths.js --analyze --organic  # только пересчёт по выгрузке, первый визит из органики
npm run test:metrika-paths
```
Ограничения: ClientID меняется при смене браузера/устройства и очистке cookie; путь по страницам внутри одного визита Logs API отдаёт
отдельной выгрузкой просмотров (здесь только страница входа каждого визита); связь с customer_id отсутствует.
