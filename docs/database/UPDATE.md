# Обновление схемы и документации БД

Этот runbook описывает обязательный порядок обновления после изменения PostgreSQL-схемы проекта. Его цель — синхронизировать миграции, техническую документацию и проверки без публикации внутренних данных и без лишних merge-коммитов.

## Чем что является

| Артефакт | Назначение |
|---|---|
| `services/**/schema.sql`, `services/**/migrations/` | Источник изменений production-схемы |
| `docs/database/config.json` | Разрешённые таблицы, представления, исключения и правила безопасности |
| `docs/database/public-descriptions.json` | Проверенные публичные технические описания |
| `docs/database/baseline.json` | Sanitized-структура для восстановления временной БД |
| `docs/database/generated/` | Автоматически сгенерированная документация; вручную не редактировать |
| `scripts/generate-db-docs.js` | Генератор документации и проверки безопасности |
| `scripts/generate-db-baseline.js` | Генератор `baseline.json` |
| `scripts/rebuild-db-docs.js` | Проверка восстановления во временной БД |
| `.github/workflows/db-docs.yml` | Проверка согласованности baseline и документации в CI |

`baseline.json` не является миграцией и не должен применяться к production-БД. CI не подключается к production и не проверяет актуальность baseline относительно него: синхронизация выполняется на VDS этим порядком действий.

## Порядок обновления

### 1. Начать с чистой рабочей ветки

Обновить `main` без создания merge-коммита и создать тематическую ветку:

```bash
git switch main
git pull --ff-only
git switch -c docs/db-<краткое-название>
```

Если в рабочем дереве есть посторонние изменения, сначала разобраться с ними. Не переносить их в коммит документации и не использовать `git add .`.

### 2. Применить и проверить миграцию

Применить изменение схемы установленным для проекта способом и убедиться, что production-БД находится в ожидаемом состоянии. `docs:db:rebuild` для применения миграций не используется.

При добавлении таблицы или представления проверить его назначение и явно добавить в `scope.tables` или `scope.views` в `config.json`. Пока объект не добавлен, режим `newObjects: "deny"` должен останавливать генерацию.

При удалении объекта удалить его из allowlist и из публичных описаний. Резервные, временные и архивные таблицы не документировать; при необходимости перечислить в `scope.excludedTables`.

Функции, материализованные представления, владельцы, роли, права, реальные данные и SQL представлений в первую версию документации не добавлять.

### 3. Обновить публичные описания

В `public-descriptions.json` указать только проверенную техническую информацию:

- что хранит объект;
- какой коллектор его наполняет;
- единицу хранения: день, месяц, запрос, URL, событие;
- назначение ключей и связей.

Production-комментарии `COMMENT ON` не копировать автоматически. Для чувствительных полей использовать ограниченный режим и явные пометки «значения не публикуются». Реальные идентификаторы, суммы, купоны, домены, IP, поисковые фразы и примеры строк не включать.

### 4. Перегенерировать baseline и документацию

Из корня проекта на VDS:

```bash
npm run docs:db:baseline
npm run docs:db
```

Не редактировать `baseline.json` или файлы `generated/` вручную. Если результат неожиданный, исправить схему, конфигурацию или генератор и повторить генерацию.

### 5. Выполнить все проверки

```bash
npm run test:db-docs
npm run docs:db:baseline:check
npm run docs:db:check
DB_DOCS_PGHOST=localhost npm run docs:db:rebuild
```

Ожидаемый результат:

- 16/16 unit-тестов пройдено;
- baseline актуален;
- документация актуальна;
- восстановление завершается с `documentationDifferences: 0`;
- временная БД удалена.

Предупреждения об отсутствии публичных описаний не являются ошибкой, но по возможности их следует устранить.

### 6. Провести ручную проверку публикации

Проверить `git status` и полный diff. Для новых untracked-файлов просмотреть содержимое отдельно: обычный `git diff` их не показывает. После явного `git add` проверить также `git diff --cached`.

Убедиться, что отсутствуют:

- секреты, строки подключения, URL/IP серверов и учётные данные;
- реальные строки, идентификаторы, суммы, купоны и поисковые фразы;
- внутренние KPI и аналитические выводы;
- SQL представлений, функции и непроверенные выражения;
- посторонние изменения, не относящиеся к задаче.

### 7. Создать атомарный коммит

В один коммит включить:

- миграцию, если она была;
- изменения `config.json` и публичных описаний;
- обновлённые `baseline.json` и `generated/`;
- изменения генераторов, тестов и workflow, если они затронуты.

Не включать посторонние файлы. Рекомендуемая форма сообщения:

```text
docs(db): update schema documentation for <краткое-название>
```

### 8. Опубликовать ветку и дождаться CI

```bash
git push -u origin docs/db-<краткое-название>
```

Создать pull request и дождаться успешного **Database documentation** во вкладке **Actions**. Не мержить при красной или незавершённой проверке.

CI поднимает временный PostgreSQL, запускает unit-тесты и `docs:db:rebuild`. Production-секреты для него не нужны.

### 9. Обновить VDS после merge

Для сохранения чистой истории предпочтителен squash merge. После merge:

```bash
git switch main
git pull --ff-only
```

Если `pull --ff-only` завершился ошибкой, не создавать merge вручную. Сначала разобрать расхождение истории и выбрать безопасный способ синхронизации.

## Если проверка завершилась ошибкой

### `Новые таблицы/представления требуют проверки`

Проверить объект на предмет публикации. Добавить его в allowlist или в список исключений осознанно. Не отключать `newObjects: deny`.

### `baseline.json ... не соответствует структуре БД`

Выполнить `npm run docs:db:baseline`, проверить diff и повторить `docs:db:baseline:check`.

### `Документация не актуальна`

Не исправлять `generated/` вручную. Выполнить `npm run docs:db`, изучить изменения и повторить `docs:db:check`.

### `Проверка безопасности` или `Непроверенное выражение`

Не ослаблять фильтры и не пытаться опубликовать объект в обход проверки. Удалить запрещённое содержимое из публичного описания или оставить только технический факт наличия объекта/ограничения.

### Ошибка восстановления или CI

Воспроизвести команду на VDS, исправить причину и повторить все проверки. Не отключать workflow и не передавать production-доступы в GitHub.

Если процесс был прерван, убедиться, что временная БД удалена. Удалять вручную только точно идентифицированную `db_docs_*` БД после проверки отсутствия подключений; другие базы не трогать.

## Критерии завершения обновления

Обновление считается завершённым только когда:

- миграция применена;
- allowlist и публичные описания проверены;
- baseline и документация перегенерированы;
- все команды проверки прошли;
- ручной diff не содержит секретов и посторонних изменений;
- коммит атомарный;
- GitHub Actions успешно завершён;
- `main` на VDS обновлён через `git pull --ff-only` после merge.
