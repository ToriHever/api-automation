# Техническая документация базы данных

Этот раздел предназначен для публичной технической документации PostgreSQL проекта: структуры таблиц и представлений, колонок, ограничений, индексов и связей.

## Источники данных

- Структура объектов должна получаться из системного каталога PostgreSQL в режиме только чтения.
- Публичные описания хранятся только в `public-descriptions.json`.
- Комментарии из production-БД не копируются в документацию автоматически: они могут содержать внутренние бизнес-правила и аналитические выводы.
- Состав объектов и правила генерации задаются в `config.json`.

## Область документирования

В `config.json` явно перечислены 64 основные таблицы и 47 обычных представлений. Из схемы `public` разрешены только `jira_issues`, `jira_issue_links` и `seo_quarterly_gsc`.

Одиннадцать резервных, временных и архивных таблиц перечислены в `scope.excludedTables` и полностью исключены. Материализованные представления и функции, включая сигнатуры и исходный код, в первой версии не документируются.

Режим `newObjects: "deny"` запрещает автоматически документировать новые объекты. Новую таблицу или представление необходимо сначала проверить и явно добавить в соответствующий список.

## Публикуемые технические метаданные

Для таблиц разрешены порядок, имена и типы колонок, nullability, identity/generated-атрибуты, проверенные значения по умолчанию, PK, FK с действиями `ON DELETE` / `ON UPDATE`, UNIQUE и краткие сведения об индексах.

Для представлений разрешены только внешняя структура, выходные колонки и типы, техническое описание и зависимости. Использовать `pg_get_viewdef` и публиковать SQL представлений запрещено.

Физические связи документируются как FK и Mermaid ER-диаграммы. Логические связи добавляются только вручную и обязаны иметь пометку «Логическая связь, не ограничение БД».

## Ограниченный режим

Для чувствительных объектов `restrictedObjects` и `restrictedPatterns` разрешают публиковать только структуру и проверенные описания без реальных значений и примеров. Это относится к клиентским идентификаторам, транзакциям, купонам, суммам, Telegram chat ID, доменам, IP, геолокации, содержимому страниц, поисковым фразам, расходам и статистике запусков.

Названия и типы `input_tokens` и `output_tokens` в `ai.runs` безопасны: это счётчики токенов модели, а не секретные ключи. Их фактические значения не публикуются.

## Выражения и определения

CHECK-ограничения, частичные индексы с WHERE и индексные выражения до отдельной проверки публикуются только как факт наличия ограничения или индекса. Нестандартные значения по умолчанию требуют проверки. Непроверенные выражения не выводятся.

## Правила безопасности

В документации запрещено публиковать:

- строки подключения, пароли, токены, имена пользователей, адреса серверов и версию сервера;
- владельцев объектов, роли, права, GRANT, REVOKE и политики доступа;
- полный `pg_dump`, тела функций и административные функции;
- реальные строки, примеры данных, размеры таблиц, количество записей и статистику содержимого;
- внутренние KPI, бизнес-выводы и непроверенные комментарии из production-БД.

Перед публикацией первой сгенерированной версии необходимо вручную проверить весь `git diff`.

## Автоматическая защита от случайной публикации

До записи файлов генератор выполняет независимые проверки:

- разрешаются только явно перечисленные объекты, а новые таблицы и представления вызывают ошибку;
- production-комментарии, SQL представлений, функции, DDL, дампы, INSERT/COPY, роли и права блокируются;
- строки подключения, URL, IP-адреса, секреты, токены, JWT, SSH-ключи и параметры окружения блокируются;
- небезопасные значения флагов в `config.json` останавливают генерацию;
- сгенерированный текст дополнительно сравнивается с исходными CHECK, частичными индексами, индексными выражениями и defaults: совпадение непроверенного выражения останавливает запись;
- сообщения об ошибках не содержат обнаруженное секретное значение или выражение.

Проверка выполняется и при `docs:db`, и при `docs:db:check`. Автоматические проверки не заменяют ручное ревью.

## Чек-лист перед публикацией

1. Выполнить `npm run docs:db`, затем `npm run docs:db:check`.
2. Проверить `git status` и полный diff. Для новых untracked-файлов просмотреть содержимое отдельно: обычный `git diff` их не показывает.
3. Убедиться, что в документацию не попали реальные значения, примеры, внутренние комментарии и непроверенные выражения.
4. Только после ручного ревью коммитить и публиковать изменения.

## Структура

- `config.json` — явные списки объектов, исключения, ограниченные режимы, политика выражений и доменные разделы.
- `baseline.json` — детерминированная sanitized-структура для восстановления временной БД, без исходного SQL и данных.
- `public-descriptions.json` — технические описания таблиц, представлений и колонок, разрешённые для публикации.
- `generated/index.md` — навигация по разделам.
- `generated/*.md` — технические таблицы, ограничения и Mermaid-диаграммы связей.

## Генерация

Запуск выполняется из корня проекта на VDS:

```bash
npm run docs:db
npm run docs:db:check
```

`docs:db` читает системный каталог PostgreSQL в read-only транзакции и обновляет файлы в `generated/`. Параметры подключения берутся из существующих PG*-переменных и не выводятся в документацию.

`docs:db:check` ничего не записывает и завершается ошибкой, если сгенерированные файлы отсутствуют, отличаются от актуальной структуры или содержат устаревшие автогенерированные разделы.

Генератор завершается ошибкой при появлении таблицы или представления вне allowlist, удалении разрешённого объекта, неизвестном описании и нарушении правил ограниченного режима.

## Воспроизводимая структура для CI

`baseline.json` содержит только технические метаданные: колонки и типы, nullability, identity/generated-атрибуты, безопасные defaults, PK, FK, UNIQUE, сведения об индексах и зависимости представлений. Исходные SQL представлений, непроверенные выражения, комментарии, функции, данные и параметры сервера в него не попадают.

```bash
npm run docs:db:baseline
npm run docs:db:baseline:check
DB_DOCS_PGHOST=localhost npm run docs:db:rebuild
```

- `docs:db:baseline` обновляет sanitized-структуру по текущей БД; `--check` только проверяет её актуальность.
- `docs:db:rebuild` создаёт уникальную временную БД, восстанавливает в ней пустую структуру техническими заглушками, формирует документацию в памяти и сравнивает её с `generated/` без записи. Временная БД удаляется в `finally` также при ошибке.
- `DB_DOCS_PGHOST=localhost` нужен при запуске на VDS, поскольку доступ к новой временной БД через внешнее имя хоста ограничен `pg_hba.conf`. В CI используется `PGHOST` временного PostgreSQL без этого override.
- Для восстановления требуется право `CREATE DATABASE` у роли проекта.

После изменения схемы нужно обновить `baseline.json` и `generated/`, затем успешно выполнить восстановление. Наличие `baseline.json` не заменяет миграции production-БД: это отдельная тестовая модель структуры, а не исходный код приложения.

## Тестирование генератора

```bash
npm run test:db-docs
```

Тесты используют только фиктивные метаданные и временные каталоги внутри `scripts/output/`. Обращение к `pg.Client` в тестах запрещено, поэтому production-БД не используется и не изменяется. Проверяются структура и связи, Mermaid, экранирование Markdown, детерминизм, allowlist, блокировка секретов и выражений, запись, повторный запуск и код ошибки `--check`.

## GitHub Actions

Workflow находится в `.github/workflows/db-docs.yml` и запускается на push в `main` и на pull request. Он использует `ubuntu-latest` и отдельный временный PostgreSQL service:

1. устанавливает зависимости через `npm ci`;
2. выполняет `npm run test:db-docs`;
3. выполняет `npm run docs:db:rebuild`, который восстанавливает структуру из `baseline.json` и сверяет документацию в памяти.

Учётные данные PostgreSQL в workflow предназначены только для одноразовой CI-среды. Production-БД, VDS, SSH и секреты проекта не используются. Отдельный `docs:db:check` после восстановления не требуется: сравнение уже выполняется внутри `docs:db:rebuild`.

CI проверяет согласованность `baseline.json` и `generated/`, но не их актуальность относительно production. Обновление baseline и документации по production-схеме выполняется отдельно на VDS.

## Текущий статус

Генератор, команды `docs:db` / `docs:db:check`, автоматическая защита и постоянные тесты добавлены. Файлы в `generated/` содержат техническую структуру текущей БД и обновляются только автоматически. Sanitized `baseline.json` и восстановление во временной БД успешно проверены, в том числе из пустой административной БД в режиме CI. Workflow GitHub Actions создан; его запуск на GitHub будет проверен после публикации изменений. Изменение схемы, `baseline.json`, публичных описаний и сгенерированной документации нужно отправлять одним изменением.
